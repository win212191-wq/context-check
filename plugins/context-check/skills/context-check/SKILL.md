# 작업 전 맥락 점검 (context-check)

## 왜 필요한가

대화가 길어지면 세 가지 실수가 생긴다.

- **용어가 미끄러진다.** 앞에서 이 방만의 뜻으로 정한 용어(품번, 시트 이름, 약어, "최종본" 같은 표현)를 일반적인 뜻으로 바꿔 읽는다.
- **요약이 뉘앙스를 지운다.** 기록이 요약되면 "보고만 해 줘"와 "고쳐 줘"의 차이처럼 작지만 결정적인 구분이 사라진다.
- **비슷한 말을 같은 말로 읽는다.** "정리"를 요약으로 원했는데 삭제를 하거나, "검토"를 표시만 원했는데 원본을 고친다. 이러면 아예 **다른 일**을 하게 된다.
- **문장 구조가 뜻을 바꾼다.** 단어를 모두 알아들어도 빠진 말(무엇을, 누구에게), 방향(무엇이 기준인가), 범위(부정, 꾸밈말, only가 어디까지 걸리나)를 잘못 읽으면 반대 일을 한다. 한국어는 생략과 조사, 어미에서, 영어는 꾸밈 범위와 대명사에서 자주 생긴다.

다른 일을 하고 나서 되돌리는 비용은 1분 동안 점검하는 비용보다 훨씬 크다. 이 스킬은 그 1분을 쓰게 한다. 다만 점검이 일을 대신하면 안 되므로, 화면 한 장 안에서 끝낸다.

## 1단계: 읽기 (묻기 전에 먼저 본다)

사용자에게 묻기 전에, 이미 답이 있는 곳부터 본다. 무게가 큰 순서는 다음과 같다.

1. **사용자가 바로잡은 기록**: "아니", "그게 아니라", "내 말은" 뒤에 오는 말이다. 사용자가 직접 정한 해석이므로 다른 어떤 근거보다 앞선다.
2. **이번 요청의 원문**: 요약이나 바꿔 쓴 말이 아니라 사용자가 쓴 글자 그대로 읽는다.
3. **뉘앙스 사전**: 개인 사전 `~/.claude/context-check/nuance-dictionary.md`가 있으면 그것을 읽는다. 이 사용자가 바로잡아 온 해석이 쌓인, 모든 프로젝트에 공통인 말버릇이다. 없으면 이 스킬 폴더의 `nuance-dictionary.md`(기본 후보표)를 읽는다.
4. **프로젝트 용어집**: 작업 폴더의 `.claude/glossary.md`가 있으면 읽는다.
5. **메모리와 지침**: `MEMORY.md`와 이번 작업에 관련된 메모리 파일, `CLAUDE.md`.
6. **세션 원문 기록 (필요할 때만)**: 대화가 요약된 흔적이 있고, 핵심 용어의 처음 뜻을 확인해야 할 때만 본다. `~/.claude/projects/<프로젝트 폴더>/*.jsonl`에서 **그 용어만** 검색해 사용자가 처음 쓴 문장을 찾는다. 전체를 읽지 않는다.

요청이 작으면 1~3만 훑어도 된다. 읽는 양은 작업이 틀렸을 때 생기는 손해에 맞춘다.

## 2단계: 정리해 보여 주기

아래 양식으로 보여 준다. 이번 작업과 관계없는 항목은 지운다. 빈 칸을 채우려고 내용을 지어내지 않는다.

```
## 🧭 작업 전 점검

### 요청 해석
- 원문: "<사용자가 쓴 그대로>"
- 복원: [누가] [무엇을] [어디에/누구에게] [어떻게] 한다  ← 구조상 걸리는 곳이 있을 때만
- 구조상 갈리는 곳: '<조사·어미·꾸밈말·지시어>' → <해석 A> (O) / <해석 B> (X)
- 갈리는 표현: '<동사나 표현>'
  - (A) <해석 1>  ← 채택
  - (B) <해석 2>
- 근거: <어떤 말이나 파일 때문에 A로 봤는지. 인용하거나 파일 이름을 적는다>
- 할 일: <구체적인 행동>
- 하지 않을 일: <B, C처럼 오해하면 하게 될 행동>

### 이 방의 용어 (이번 작업에 쓰이는 것만)
| 용어 | 이 방에서의 뜻 | 근거 | 헷갈리기 쉬운 것 |
|---|---|---|---|

### 확정 사항
- <이미 정한 규칙, 사용자가 바로잡은 내용>

### 확인이 필요한 점
- <근거가 없거나 서로 충돌하는 것만>
```

양식을 채울 때의 원칙은 다음과 같다.

- **"하지 않을 일"은 빼지 않는다.** 이 칸이 다른 일로 새는 것을 막는 핵심이다. 오해했을 때 하게 될 행동을 구체적으로 적는다. 예: "서식 변경 안 함", "행 삭제 안 함", "원본 파일 수정 안 함".
- **확정과 추정을 나눈다.** 사용자가 말했거나 정정한 것은 확정이다. 내가 짐작한 것은 "(추정)"이라고 붙인다.
- **빈칸은 근거로 채운다.** '복원'에서 빠진 말을 채울 때, 근거가 없는 칸은 "(추정)"으로 표시해 사용자 눈에 띄게 한다. 오해는 대부분 근거 없이 빈칸을 혼자 채울 때 생긴다.
- **사용자의 단어를 그대로 쓴다.** 내 말로 바꾸는 순간 뜻이 미끄러진다. 사용자가 "BRKT-A"라고 했으면 "A 브래킷"으로 바꿔 부르지 않는다.
- **근거에는 출처를 단다.** "앞에서 '도면값 기준'이라고 하심"처럼 짧게 인용하거나 파일 이름을 적는다.

## 3단계: 진행할지 판단하기

| 상황 | 행동 |
|---|---|
| 해석이 하나로 분명하고 되돌릴 수 있는 작업 | '요청 해석' 칸만 3줄 정도로 보여 주고 바로 진행한다 |
| 해석이 둘 이상이고 결과가 크게 달라짐 | 멈추고 묻는다 |
| 삭제, 덮어쓰기, 일괄 수정, 외부 전송 | 해석이 분명해 보여도 '할 일'과 '하지 않을 일'을 보여 주고 확인받는다 |
| 근거끼리 충돌함 (예전 지시와 지금 지시가 다름) | 둘을 나란히 보여 주고 어느 쪽인지 묻는다 |

물을 때는 열린 질문("어떻게 할까요?")보다 **해석 후보를 선택지로** 준다. AskUserQuestion이 있으면 그것을 쓰고, 한 번에 4개까지 묶는다. 선택지마다 "이걸 고르면 무엇을 하고 무엇은 안 하는지"를 한 줄로 붙인다. 사용자가 "그냥 해"라고 하면 채택한 해석으로 진행한다.

## 4단계: 배운 것 기록하기

점검이 쌓여야 같은 오해가 반복되지 않는다.

- **사용자가 해석을 바로잡았거나 후보 중 하나를 골랐을 때**:
  - 프로젝트와 관계없는 말버릇이면 개인 사전 `~/.claude/context-check/nuance-dictionary.md`의 '확정' 표에 한 줄 추가한다. 파일이 없으면 이 스킬 폴더의 `nuance-dictionary.md`를 그 자리에 복사한 뒤 추가한다. 스킬 폴더 안의 파일은 고치지 않는다. 플러그인을 업데이트하면 덮어써지기 때문이다.
  - 이 프로젝트에만 쓰는 용어면 작업 폴더의 `.claude/glossary.md`에 추가한다. 파일이 없으면 아래 형식으로 새로 만든다.
- **파일을 쓸 수 없는 환경**(예: claude.ai 채팅)에서는 메모리 기능이 있으면 메모리에 한 줄로 저장하고, 없으면 답 끝에 "📌 용어집에 추가할 줄" 표를 붙여 사용자가 직접 옮기게 한다.
- **기록하지 않는 것**: 내 추정, 아직 확인받지 않은 해석, 이번 대화에서만 의미 있는 일.
- **이미 있는 줄과 충돌할 때**: 새 줄을 더하지 말고 기존 줄을 고친 뒤 날짜를 바꾼다.
- 기록했으면 "뉘앙스 사전에 '정리 = 요약(삭제 아님)'을 추가했습니다"처럼 한 줄로 알린다.

프로젝트 용어집 형식은 다음과 같다.

```
# 용어집 — <프로젝트 이름>
| 용어 | 이 프로젝트에서의 뜻 | 헷갈리기 쉬운 것 / 아닌 것 | 확정일 |
|---|---|---|---|
```

## 문장 구조 판별 요령

단어를 모두 맞게 읽어도 단어를 엮은 구조를 잘못 읽으면 뜻이 뒤집힌다. 요청 문장을 아래 다섯 기준으로 훑는다. 어느 언어에나 쓰는 기준이다.

| 기준 | 스스로 던질 질문 | 예 |
|---|---|---|
| 방향 | 무엇이 기준이고 무엇을 바꾸는가? | "도면 기준으로 엑셀 맞춰" ↔ "엑셀 기준으로 도면값 확인" / "replace A with B" |
| 범위 | 부정, 꾸밈말, 나열, only가 어디까지 걸리는가? | "전부 고치지 마" / "A안과 B안 수정본" / "Only fix errors in sheet 2" |
| 생략·지시어 | 빠진 주어, 목적어, 받는 사람은? "그거", "it"은 무엇인가? | "확인하고 보내줘" / "update it" |
| 연결 | 순서인가, 이유인가, 조건인가? | "검토해서 정리해줘" / "fix if needed" |
| 말투 | 지시, 제안, 질문, 허락 중 무엇인가? | "~해볼까?", "~해도 돼" / "Can you check this?" |

- 걸리는 곳이 있으면 '요청 해석'의 **복원** 줄에 빠진 말을 대괄호로 채워 문장을 다시 쓰고, **구조상 갈리는 곳** 줄에 후보를 적는다. 걸리는 곳이 없으면 두 줄 모두 생략한다.
- 대조 조사도 본다. "엑셀**은** 고치지 마"에는 "다른 것은 고쳐도 된다"는 뜻이 숨어 있을 수 있다. "엑셀**도**", "엑셀**만**"은 범위가 또 다르다.
- 한국어 문장에 영어 용어가 섞이면("보고서 v2 review") 용어의 경계와 꾸밈 범위를 따로 확인한다.
- 오타나 구어체("해바")를 다른 뜻으로 과하게 해석하지 않는다.
- 유형별 예시가 더 필요하면 `references/sentence-structure.md`를 읽는다.

### 번역하거나 원문을 검토할 때

오해는 요청뿐 아니라 **결과물**에도 남는다. 영문 원본을 번역하거나 번역본을 검토할 때는 원문 문장도 같은 다섯 기준으로 본다.

- 원문이 두 가지로 읽히면 혼자 하나를 골라 조용히 번역하지 않는다. 채택한 해석으로 번역하고, 다른 해석이 가능하다는 점을 원문과 함께 기록한다. 사용자가 정한 오류 기록 자리(예: '확인 필요' 목록)가 있으면 그곳에 적는다.
- 예: "Check the thickness of the plate and the bracket marked A"에서 'marked A'가 bracket에만 걸리는지, 둘 다에 걸리는지에 따라 번역본의 뜻이 달라진다.

## 단어 뉘앙스 판별 요령

해석이 갈리는 표현은 다음 네 가지를 기준으로 쪼개면 후보가 잘 나온다.

- **범위**: 보고만 하는가, 고치기까지 하는가?
- **대상**: 내용(값, 문장)을 바꾸는가, 형식(서식, 순서, 배치)을 바꾸는가?
- **파괴성**: 추가하는가, 아니면 삭제하거나 덮어쓰는가?
- **결과물**: 채팅으로 답하는가, 파일을 바꾸는가, 새 파일을 만드는가?

말투에서도 신호를 읽는다.

- **"~알겠어?", "~이해했어?"**: 이해했는지 확인하는 질문이다. 실행 요청이 아니므로 설명으로 답한다.
- **"~해 볼까?", "~할 수 있어?"**: 제안이거나 가능한지 묻는 말일 수 있다. 앞뒤 맥락이 실행 쪽이 아니면 실행 전에 확인한다.
- **"~부터 해 보자"**: 순서를 지정한 것이다. 그 단계에서 멈추고, 다음 단계로 넘어가지 않는다.

비슷하게 생긴 말도 조심한다. 철자, 품번, 시트 이름, 파일 이름이 비슷하면 용어 표의 '헷갈리기 쉬운 것' 칸에 나란히 적고 차이를 한 줄로 쓴다.

## 하지 말 것

- 점검을 핑계로 일을 늘리지 않는다. 점검 블록은 화면 한 장 안에서 끝낸다.
- 대화 전체를 요약하지 않는다. 이번 작업에 필요한 용어와 결정만 꺼낸다.
- 분명한 요청에 질문을 쏟아 내지 않는다. 불필요한 질문도 사용자의 시간을 쓴다.
